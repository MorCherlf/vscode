# 双插件生态验证计划与阶段推进文档

日期：2026-10-29。状态：待执行。本文配套 [可行性报告](README.md)，全部通过标准都是计划，不代表已通过。沿用此前“交付代码不等于验收”的规则；不擅自替换现有 M0–M8 和 G01–G12。PoC 形成决策后，再更新正式路线和目标。

## 1. 验证记录与决策规则

每项记录产品 SHA、VS Code/DSH SHA、容器/Node/OS/架构、锁文件/包哈希、profile、插件版本、原生对照环境、命令、操作步骤、预期、实际结果、日志/截图和限制。真实账户、私钥、完整会话和令牌不进入证据；使用测试账户和合成数据。

兼容等级按“未测试、安装成功、激活成功、主要功能通过、全部约定场景通过、受限、失败”分别标记。每个插件有自己的必测场景，安装/激活不能替代功能验收。平台和容器分别记录，Chromium mock 不能代替原版 Electron 或 Mac WKWebView。

冻结样本前确认包的合法来源和运行所需外部服务；缺少凭据的场景记为未验证。若原生对照环境也失败，先修正 fixture/版本选择并留下记录，不直接把产品失败算通过。任何修改必测范围都要先更新版本化清单和理由，保留旧结果。

架构决策采用 ADR：候选方案、证据、支持范围、放弃/保留的选项、维护成本、回退方法和影响的旧目标。推荐主线与 Tauri 候选共享原组件和插件测试；不得为同一功能各写一套 UI。

## 2. POC-01：原组件基线与真实复用

**目标：** 用原 Sessions/Workbench 组合启动 Agent-first 窗口，证明运行的是原 ChatWidget、ChatInputPart 和会话列表，而不是重写版本。

**输入：** 原 VS Code 固定提交、现有构建脚本、ChatView/Widget/Input/列表源码、原主题与服务。先使用原 Electron 平台，不同时解决所有 Tauri 差异。

**任务：**

1. 记录原版完整工作台与 Sessions 的功能/服务差异，固定产品主界面的首轮支持范围。
2. 在原 composition root 中增加最小产品贡献/启动选项，复用原服务和渲染路径，不复制核心组件到新目录。
3. 建立可定位的调用链/断点或源码映射证据，记录原实例创建、使用文件和产品差异文件。
4. 用确定性 provider 验证输入、流式文本、代码块、工具调用/审批、停止、会话切换、变更审阅；再接一个合法可用的真实模型任务。
5. 比较原生对照界面，验证快捷键、IME、多行、粘贴、焦点、滚动、主题和无障碍名称；默认隐藏的编辑区保留真实服务。

**交付物：** 可启动基线、原组件来源清单、服务差异表、原版/产品对照证据、最小产品补丁及构建说明。

**验收：** 三个核心原组件都在实际调用链中；主交互无需现有 React App/Transcript 运行；确定性场景逐项通过；真实模型场景单独记录。不得用只加载一个静态页面、截图相似或仅复用 CSS 通过本项。

**失败处理：** 恢复缺失服务与原工作台组合，先减少布局改动。若“完全删除编辑器代码”是失败原因，在 ADR 中明确与原组件/插件目标的冲突，不能偷偷重写输入框。

## 3. POC-02：原宿主与代表性 VS Code 插件

**目标：** 原样安装、激活、运行有真实功能的 VSIX，确认完整 ExtHost/MainThread 对端与界面承载面。

**输入：** POC-01、原扩展宿主、固定 VSIX/源码构建清单、当前 [manifest 审计](evidence/plugin-manifests.json)。静态审计样本不直接当成已安装样本。

**任务：**

1. 选定可授权获取的样本，固定版本、hash、`engines.vscode`、运行位置、原生模块和必测功能。
2. 首轮至少覆盖：声明式主题/语言、命令/配置、文件/workspace、TreeView、WebviewPanel、WebviewView、languageModelTool，以及一个需编辑器/文档的插件。
3. 加入 Cline、Continue 的适用版本，先验证它们作为独立插件的原交互和主要任务；不要求 DSH 控制其内部循环。
4. 加入一个 `extensionKind: ["ui"]` 的 Node fixture、一个 WebWorker fixture、一个需取消/卸载的工具 fixture；fixture 用于协议边界，不能替代真实插件。
5. 审计 Sessions 的启用和缺失 feature 检查；恢复必要原版视图承载面，保留不能支持的类别列表。
6. 执行安装、升级、重启后恢复、禁用、卸载、workspace trust 切换、宿主崩溃/重启；确认没有重复激活/资源泄漏。

**交付物：** 扩展支持清单、实际运行宿主/服务图、原生对照结果、API/界面缺口、核心补丁清单。

**验收：** 冻结样本的必测项全部通过，或明确阻断 F2 的失败；真实视图/文档行为与对照一致；UI-only Node fixture 不能被篡改 manifest 强行迁到 workspace。仅“扩展未报错”不算通过。调试、Notebook 等未纳入范围的能力必须明示，不能宣传全生态兼容。

**失败处理：** 优先恢复原平台服务和工作台贡献。需要广泛模拟 API/伪造编辑器时停止该适配路线，回到原生组合，不扩充手写 `vscode` 桩。

## 4. POC-03：原生 DSH、profile 与会话控制

**目标：** 运行原生 DSH 包与 profile，证明工具以外的插件、审批、持久化、取消和多会话隔离可用。

**输入：** 固定 DSH SHA/版本、匹配 Node、独立 home/profile/依赖、SDK 和原 Agent runtime 接口。先以官方 `sdk`/`web` 组合为对照，不把 `sdk-minimal` 结果外推到完整 profile。

**任务：**

1. 固定 runtime、Cordis、bundles、profile/patch 与依赖完整性；以测试目录启动，与个人 DSH/VS Code 配置隔离。
2. 用官方 SDK 验证启动、握手、工具/LLM 插件、事件、一次性审批、提问、持久化恢复与 shutdown，记录 stdout 是否始终为协议。
3. 至少使用原 LLM retry、一个 prompt/context 或 compaction 插件、一个工具/策略插件，确认非 tool 插件参与实际链路。
4. 明确 SDK 缺少 prompt-cancel/per-session-close；设计版本化 Cordis 驱动，使用原 Agent 控制和拥有者 handle，而不是修改 loop 私有字段。
5. 同进程开启 A/B 两个会话，取消 A 的模型流/工具/待审批/排队输入，B 继续完成；分别测 followup、恢复和关闭，不以全进程 kill 代替。
6. 取消后送达迟到批准/结果，关闭中收到新输入，工具不响应取消、子 Agent 仍运行、宿主崩溃等场景，记录实际终态与清理。
7. 验证 profile/bundle 覆盖顺序、禁用/卸载 effects；profile 不支持 HMR 时正确要求重启。

**交付物：** 原运行时集成、受支持 profile 清单、驱动协议草案/实现、会话状态机、控制与恢复证据。

**验收：** 原插件/服务与对照行为一致；审批拒绝不能执行；迟到批准失效；取消 A 不结束 B；驱动能区分入队、turn 结束、idle 和失败；持久化恢复交回 DSH，损坏/版本不兼容时报告失败，不静默建新会话代替。取消超时/隔离升级规则必须可见且有测试。

**失败处理：** 先交付 SDK 原生集成的有限能力，并保留多会话控制为阻断项。可以将缺失控制贡献 DSH 上游；在缺口解决前，不把“每会话一个进程并关闭进程”表述为共享运行时逐会话取消已经实现。

## 5. POC-04：工具、上下文与权限桥

**目标：** 双向调用有用能力，同时保留各自权限和结果语义。

**输入：** POC-02/03、原 `vscode.lm` 工具 API、DSH 原执行链、产品 bridge v1 和命名空间。

**任务：**

1. 原工具目录只发布允许共享的能力，保留来源、schema、workspace/profile、运行位置与支持限制；阻断循环导出。
2. DSH 经桥接扩展调用 VS Code 工具，分别验证真正 ChatRequest 的 token 与全局 `undefined` token 路径；不伪造 token。
3. VS Code 工具调用 DSH 能力时，仍经过 DSH pre-execute/guard/execute/finalize，不能直接调用绕过 guard 的实现函数。
4. 测无权限、一次性批准、拒绝、取消、断连、工具参数变化、迟到结果、崩溃后状态未知和重复提交。
5. 保留 Text/结构化/二进制/PromptTSX 等结果的类型；无法表示的类型明确返回能力不支持，不丢弃后返回成功。
6. 上下文共享用有 URI、文档版本和边界的快照；更换工作区、文件变化、撤销信任后使旧授权/内容失效。
7. 不让 DSH 深层 hooks 冒充能修改 Copilot/Cline/Continue 内部循环；UI/目录注明每个能力的实际运行时。

**交付物：** bridge v1 契约、兼容/拒绝类型表、跨运行时调用链、权限与取消测试、开发者示例。

**验收：** 每个动作仅有一个执行拥有者；deny 保留、参数变更需要重新授权、取消后的批准无效、未知副作用不自动重放、调用环路被拒绝；每种支持结果在双方对照一致，不支持类型有明确错误。产品托管的账户/模型长期凭据不进入 Webview、命令行参数或普通日志；必要短期连接授权与 provider 主密钥分开验证。

**失败处理：** 收窄 bridge 的公开能力类型，继续保持两个原生生态可独立运行。不要通过关闭原审批或降级全部结果为字符串扩大覆盖率。

## 6. POC-05：原 DSH 前端与强插件开发体验

**目标：** 原 DSH client 插件在产品中使用原 loader/renderer，而不是重新实现其页面。

**输入：** POC-03、完整 Web profile、匹配的 client bundles/assets/shared modules、原 Code OSS Webview 或独立页面承载面。

**任务：**

1. 保留 boot graph、release version/commit 身份、模块表、外部依赖、locale/remote/slots 和资源解析。
2. 运行原插件设置页及至少一个有实际状态/操作的前端插件，对比原 DSH Web 对照环境。
3. 测启用、禁用、卸载、重新启用、后端重连、host/client release 不一致、缺 bundle、加载失败和前端同步重试。
4. 验证主题、键盘焦点、滚动、IME、导航和错误呈现；记录完整原 client 页面与主 Agent UI 的边界。
5. 为主动适配的新插件提供最小 SDK 示例：共享逻辑、VSIX 包装、DSH 包装，可撤销注册、类型/schema、诊断与版本策略。
6. 动态 runner 作为后续受限能力，单独验证原 VM/guard/审批，初期不默认开放。

**交付物：** 原前端承载、client 版本/资源证据、插件诊断页、双入口开发示例和支持范围。

**验收：** 原包内容/哈希未为兼容被改写；真实原 client 插件运行；跨 release 不混装；重复启用无重复效果；后端已激活与前端失败分开显示。独立页面是第一阶段可接受的产品边界，无需为了外观统一重写插件。

**失败处理：** 暂时仅承诺 DSH 后端/profile 兼容，前端能力保留“未支持”；不要把 SDK-only 无 UI 运行当成前端兼容通过。

## 7. POC-06：双上游升级与回退演练

**目标：** 用实际不同提交验证产品可持续跟进上游。

**输入：** 通过前述基础场景的产品基点、原上游历史、产品 patch 清单、runtime/插件锁、合成会话数据。

**任务：**

1. 在独立升级分支分别选择新的 VS Code 和 DSH 提交，记录原/新 SHA、选择原因及 API/协议/schema 变化。
2. 合入 VS Code 上游，逐项处理原 UI、平台服务、ExtHost/MainThread 和 AHP 的冲突；不强制推送共享分支。
3. 升级 DSH 匹配组合，审阅 profile/plugin API、client graph、控制驱动和持久化迁移；不混搭核心包。
4. 跑原组件、全部冻结插件必测项、双向工具、取消/恢复及原前端场景；原生对照环境也升级。
5. 演练失败升级恢复：停止相关宿主、恢复完整版本元组/锁与适配的数据备份，再打开既有测试会话。
6. 记录修改面积、冲突热区、人工耗时、失败修复和未解决项，评估桥接边界是否稳定。

**交付物：** 两个真实升级记录、冲突与兼容报告、可执行回退说明、产品补丁/依赖版本 manifest。

**验收：** 既有必测项通过；升级前数据按声明路径恢复；回退后原功能可用；没有靠删除失败样本或修改其业务代码通过。明确区分“Git 无冲突”“编译通过”“功能兼容”三种结果。

**失败处理：** 阻断版本发布，隔离不兼容插件/运行时组合；优先把热区修改迁为服务/贡献适配。若升级持续需要维护大份复制的 Chat/API/loop，重新评审架构。

## 8. POC-07：Tauri 原组件承载、Mac 性能与发行

**目标：** 决定 Tauri 是否能以相同原组件和兼容范围成为主容器，提供真实 Mac 数据。

**输入：** POC-01/02 的原组件与真实插件场景、原 Web Sessions create 入口、匹配的自有 Code OSS Node 服务/宿主、已有 Tauri supervisor。

**任务：**

1. 原 Web Sessions/Workbench 在 WKWebView 中启动，调用链与 Electron 对照一致，不能换回 React 原型完成缺失功能。
2. 分别验证 WebWorker、workspace Node、UI-only Node 三类宿主；记录原 Browser 工厂缺 LocalProcess 的适配方案和代码差异。
3. 完成原 Webview 的 service worker/worker、CSP、iframe、资源 URI、消息、恢复、文件下载、外链/深链接与登录回跳验证。
4. 验证原终端/PTY、文件监控、多窗口、生命周期、崩溃、更新和所有子进程清理；扩展可能携带的二进制/原生模块按实际 Node ABI 测试。
5. 原 DSH 后端与前端能力分别运行；全局上下文/审批不能进入错误窗口或会话。
6. 使用相同插件/任务比较 A/B：首次完整下载与安装占用、冷/热启动、空闲和任务峰值内存/CPU、工具与输入响应；纳入全进程树、runtime、缓存和依赖。
7. 性能建议初样本：固定设备/电源模式，冷启动至少 30 次，内存空闲稳定窗口至少 5 分钟，真实任务至少 10 次；报告分布和 p95，明确样本量及波动。首轮数据用于确定预算，不直接沿用原百分比门槛。
8. 无开发环境的 Mac 完成安装、启动、签名/公证、Keychain、真实账户和任务、更新失败回滚。缺少正式发行身份时记录为未验收，不能用未签名开发包替代。

**交付物：** A/B 同能力功能表、WKWebView 原生证据、性能原始数据、平台补丁与成本表、容器选择 ADR、发行缺口。

**验收：** 必选兼容场景与原组件门禁通过；所有进程/依赖计入测量；核心行为和权限不为性能结果缩水。是否采用 Tauri 依据兼容范围、维护成本与实际收益共同决定；未达到收益目标可保留 Electron，不把硬换容器设为产品成功条件。

**失败处理：** 对平台缺口限定两轮有记录的实验后评审，停止无限扩大平台模拟层；保留 Electron 主线继续后续工作。签名/账户缺口按原发布门禁保持未通过。

## 9. F0–F4 推进工作包

### F0：原组件与范围基线

输入为报告、原版源码和现有 Host/protocol 成果。先执行 POC-01、冻结第一批 VSIX/DSH 场景及许可来源，列出默认 Agent 界面、兼容工作区和暂不支持能力。交付原生基线、复用证据、范围清单与 ADR 草案；POC-01 核心场景通过后进入 F1。若基础依赖仍不清楚，继续补服务图，不开新 React 替代页。

下一步：从原 Sessions 启动入口和服务组合建立最小可复现基线；在代码实现前核对现有构建/任务输出，避免重复全量编译。

### F1：宿主、桥接与容器决策

输入为 F0 基线。执行 POC-02/03/04，并对 POC-07 的原 Web UI、三类宿主、Webview 开展前置实验；研究可以分工，但修改共享核心时保持提交边界。交付可比较的 A/B 缺口、双原生加载结果、桥接契约与取消状态机。必选兼容场景通过、或有明确保留 Electron 的决策后进入 F2；不得因 Tauri 平台缺口阻止已验证的原生路线推进。

下一步：先验证最容易证伪路线的 UI-only Node host、原 Webview 和 DSH 多会话取消；这些通过前不投入大规模外观整合。

### F2：限定范围双生态 Alpha

输入为 F1 ADR 和冻结接口。完成原扩展安装/管理、必要的 views/兼容区、原 DSH profiles/包管理、统一能力目录与会话投影；保留原状态所有者。建议冻结至少 20 个 VS Code 样本和 10 个 DSH 组合场景，分别覆盖真实插件和边界 fixture，不用数量掩盖缺失类别。交付每插件/平台的支持表、完整工作流和故障恢复证据；全部必测项通过才可称限定范围 Alpha。

下一步：按缺口先恢复原承载面，再扩充桥接功能；不新增无法诊断来源和权限的隐式能力。

### F3：强插件支持与可维护性

输入为稳定 Alpha。完成 POC-05/06、版本化产品 SDK、插件诊断与开发示例、原 DSH client 承载、升级/回滚流程。交付两个不同上游的真实升级记录、运行时完整版本 manifest 和开发者兼容指南。原客户端插件及升级门禁通过后进入 F4；未通过时限制承诺范围，明确留在后端兼容等级。

下一步：把最常出现的适配需求归纳成少量稳定接口，避免逐插件增加内部特例。

### F4：Mac Beta 与发行

输入为经过升级演练的版本组合。完成 POC-07 全部真机、签名、真实账户、插件许可/来源、性能和更新回滚门禁；按采用的容器记录结果。交付可分发包、完整支持范围、已知限制和可复现证据。发布不以“任意插件兼容”命名，而以具体 VS Code/DSH 版本与插件类别承诺。

下一步：用全新用户环境验收，冻结发行版本元组；失败只修阻断项，不在发布前新增另一套 UI/协议。
